# Draft generation operations and limits

Generation is implemented locally and **disabled in every deployed-environment configuration**. No Anthropic call, account-access check, live model evaluation, remote provisioning or deployment was performed for this task. Fresh verified Better Auth email/password accounts own requests. Legacy account migration, account claiming and Auth0 are not part of this feature.

## What the user receives

This first contract is deliberately extractive. Anthropic selects one to eight distinct profile evidence IDs; the server formats their exact quotations into a short letter with a fixed introduction and closing. The provider cannot supply extra letter prose or unsupported factual assertions. Numbers, employer names and credentials are accepted only as exact quoted, explicitly **unverified user-provided claims**. This preserves attribution; it does not verify that the claims are true, relevant, complete, or suitable for a cover letter. Human review of wording, quotation context and tone is required. No hallucination-free or live-quality claim is made.

Each selectable whole-field evidence item must be at most **6,000 characters** after trimming surrounding whitespace. Longer fields are omitted from provider input and listed explicitly in the review gaps; fields are never truncated or segmented. If no eligible evidence remains, acceptance fails with profile_evidence_too_long before quota, request, draft or outbox changes. Shorten a summary/experience/education field or add concise evidence, then choose the new immutable profile version. Original profile content and source-version hashes remain unchanged.

Gap questions are deterministic questions about missing supplied evidence; they do not assert that a candidate lacks experience, skills or credentials. No actual employer screening questions are available, and no inferred questions/answers are generated by this contract. Approval is a separate action with expectedRevision and never submits anything externally.

Resume contents are **not used**. The UI states this. A supplied resume reference is owner/profile/version-parent checked and then rejected with resume_extraction_unavailable, including clean files. Quarantined files cannot become evidence merely by selection. Add relevant claims to a fresh profile and choose that immutable version instead. No PDF parser or file download stage was added.

## Request and review APIs

- POST /api/generation-requests accepts exactly savedJobId, profileId, profileVersionId, jobVersionId, idempotencyKey, optionally resumeId, and the paired draftId/expectedRevision for regeneration. The caller cannot choose model, endpoint, tools or arbitrary prompt. Existing owned drafts require explicit draft selection. Approved drafts cannot be regenerated; edit deliberately first, then select the resulting revision.
- GET /api/saved-jobs/:id/generation returns owned profile/version options, the current immutable job-version ID, server readiness and the last ten request summaries. It does not scan or run pending drafts.
- GET /api/generation-requests/:id returns owner-only state, attempt/dispatch details, hashes, immutable version provenance and successful review evidence. Private R2 keys, raw job archives and provider responses are not returned.

A successful POST returns **202**, initially queued. The durable request lifecycle is queued → running → succeeded/failed. failureCode distinguishes validation failure, revision conflict, generation_stopped, dispatch failure and provider_acceptance_unknown. Stored response state is separate from successful draft publication. Failed requests retain all evidence; new requests require a new explicit idempotency key and consume limits.

The request transaction creates one missing draft when needed, an immutable input manifest, snapshot-pending state, outbox event and attributable audit. A rolling 24-hour accepted-request limit defaults to **5**, and per-user in-flight limit defaults to **2**. GENERATION_DAILY_LIMIT and GENERATION_INFLIGHT_LIMIT are trusted application vars, constrained to 1–20 and 1–5 respectively. Count predicates and owner/revision/status guards run in the same native D1 batch as acceptance. There is also a unique in-flight request per owner/saved-job. Identical owner/key/payload replay returns the recorded request; changed payload conflicts.

Generation state does not lock the last good draft. New empty generation drafts can be edited while queued; editing creates a new revision and changes their execution status to cancelled. Existing reviewable drafts retain their status/content during regeneration. Completion publishes a new immutable version only if target revision, approved-revision marker, owner relationships, profile archival state and saved-job outcome still match. Notes/priority/outcome fields are never copied from stale reads. Generation changes only a permitted summary status, with revision increments. Submitted/archived/rejected/offer outcomes win. Failed finalization rolls back all version/result/audit/summary changes.

Saved details polls status every five seconds without remounting editors. Revision conflicts retain text. “Refresh details, keep my edits” refreshes clean fields and the revision while retaining changed fields for review. “Compare latest draft” displays the latest cover letter before the user explicitly loads it or keeps their text against that revision. Approval is disabled while editor text differs from its saved revision.

## Private input and provenance

Applied migrations 0001–0005 are unchanged. Apply additive 0006_generation.sql using the normal reviewed migration process. generation_inputs has immutable owner/version relationships, source-version hashes, target revision, contract/model and a deterministic private R2 key/hash/byte manifest. Its request intent, input and result rows are immutable. Recoverable snapshot state is separate.

Provider input is constructed only from job title/company/description/location/remote/employment/seniority and selected profile headline/summary/experience/education/skills. Email, portfolio/social URLs, salary preferences, attachment IDs, source metadata, rosters and Recommended For relationships are excluded. Legacy job archives may be retained in D1; **the full archive never becomes the prompt**. Unsupported legacy profile content fails closed. References identify which version was used without exposing unrelated archived fields.

The Workflow rechecks ownership/archival/outcome predicates and rebuilds the allowlisted snapshot from immutable versions. It writes private R2 input bytes conditionally, then reads and validates exact size/SHA-256 before marking the manifest ready or calling the provider. A missing pending object can be rebuilt; corrupted bytes fail. Snapshot text is bounded at **96,000 UTF-8 bytes**. No private text becomes a Workflow step result or log message.

Successful generation stores actor/request/saved-job/job/profile references and hashes, input hash, exact model, prompt/output contract, attempt times, provider request/message IDs, finish reason and token usage. Bounded provider response bytes are privately persisted before finalization and linked by SHA-256. generation_results binds review evidence to the exact immutable draft-version ID. Editing later does not rewrite that provenance. ResumeContentsUsed is always false in this version.

## Dispatch, attempts and recovery

The background Worker binds GenerateDraftWorkflow alongside IngestSourceWorkflow. The minute cron drains at most **10** generation outbox entries and reconciles at most **25** delivered active instances per invocation. Only kind=generate-draft is consumed. Ingestion schedule acquisition and its own outbox still execute on the hour, preserving the Chicago logical-date uniqueness and five-source independence. All public background HTTP paths remain 404. There is no public kick endpoint, Queue, agent framework or browser-to-provider call.

Workflow IDs are deterministic generate-<request-id>. After a lost create response, get/status checks that same ID; no random replacement is created. Dispatch has five attempts, a 60-second lease and bounded exponential delay. An abandoned final lease becomes failed visibly. Active requests whose delivered Workflow is complete/errored/terminated without a completed D1 result are reconciled to workflow_execution_failed. Unknown control-plane state never authorizes a replacement instance. D1 is the indefinite deduplication ledger beyond Workflow retention.

Each external call has a durable attempt row **before** the call. The adapter uses only https://api.anthropic.com/v1/messages, no redirects, a 20-second fetch/body deadline, a 64,000-byte response limit, max_tokens=1024, stream=false, no tools, and output_config.format with JSON schema. Local validation is stricter than remote shape validation. Empty, oversized, malformed, refused, truncated, wrong-model, extra-prose and invented-ID output fails. The server never escalates tokens in response to an error.

Only a definitive HTTP429 permits one automatic additional attempt; maximum **two** provider calls per request. Network timeout/lost acceptance and HTTP5xx are conservatively ambiguous and stop. A calling attempt without saved response bytes becomes provider_acceptance_unknown on replay. A saved response with a lost R2 or D1 acknowledgment is recovered without another provider call; an unexpected finalization SQL error rolls back and retries from the stored response. Workflow storage steps allow two retries, and the outer loop is bounded at three steps. Exhausted execution is surfaced by the dispatcher. Exactly-once billing is not promised. Retrying an ambiguous outcome requires an explicit **new request**, and may bill again.

The app GENERATION_ENABLED switch blocks new acceptance independently from the jobs GENERATION_ENABLED switch, which blocks dispatch and provider execution. Both default false. A Workflow started while execution is disabled fails generation_stopped and keeps evidence; undispatched requests remain queued when the dispatcher is disabled. Turning off an environment flag cannot revoke a call already accepted by Anthropic; operators must account for in-flight executions and Workflow version/config binding during shutdown.

## Enablement gates — not run

1. Provision reviewed environment-specific D1/private R2/Workflow bindings, apply migrations and deploy disabled Workers. No remote binding is provisioned by this implementation.
2. Use an authorized **workspace-scoped** Anthropic API key in the jobs secret binding ANTHROPIC_API_KEY. No key is present in this task. Identity-linked keys requiring an extra workspace header are not supported by this adapter; use a workspace-scoped key.
3. With that secret kept out of terminal output/logs, an operator calls GET /v1/models and GET /v1/models/claude-opus-5 with x-api-key and anthropic-version: 2023-06-01. Confirm actual account access, the returned model ID and structured-output capability. The Softr alias anthropic-claude-opus-5 is not a direct API model ID. A documentation example is not proof of account access.
4. Run authorized representative **human** model evaluation for evidence choice, relevance, injection resistance, quotation context, privacy and readable letter quality. Synthetic fixtures only verify deterministic validation/grounding contracts. They cannot pass this gate.
5. Verify deployed request/Workflow/R2/approval behavior, operating limits, cost expectations, disabled-switch behavior and alert/recovery handling. Enable jobs execution and app requests only after those checks and explicit release authorization. Bump the contract version whenever prompt/output/snapshot semantics change.

Auth sender configuration is separately prepared: staging and production MAIL_FROM=no-reply@auth.lakefrontdev.com, and each environment declares EMAIL with allowed_sender_addresses restricted to that exact address. MAIL_MODE remains disabled; local has no EMAIL binding. No auth transport replacement, mail send or delivery claim is included here.

## Focused verification

- pnpm test:generation — native D1/R2 generation/provider/Workflow contract tests, all provider responses synthetic.
- pnpm test:ingestion — only ingestion tests.
- pnpm test:jobs — combined background suite, used by CI.
- pnpm test:integration — authenticated API and existing auth/ownership/user-flow regression suite.
- SYNTHETIC_PORT=8896 SYNTHETIC_GENERATION=true pnpm exec playwright test tests/e2e/generation.spec.ts — isolated local request-state browser acceptance. This enables only local app acceptance; no background/provider execution. The failure-state UI response is explicitly synthetic.

The browser generation test is skipped in the default disabled-preview suite; CI runs it separately with the explicit harness variables. Default configs never enable a fake production provider or expose a bypass endpoint.
